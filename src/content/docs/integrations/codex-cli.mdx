OpenAI's Codex CLI talks to providers through the Responses API, which OpenPike serves at `/v1/responses`. Add OpenPike as a custom model provider in Codex's config, and every Codex request goes through your virtual key, budgets and Logs.

<Aside type="caution" title="Providers that serve Responses">
OpenPike passes Responses requests through without translating them, so Codex works through OpenPike with models from **OpenAI, xAI, Groq and OpenRouter**, the providers that serve the Responses API themselves (`/v1/models` entries list the `responses` format). xAI, Groq and OpenRouter are Available from their own docs, not yet tested live by OpenPike, and Groq's and OpenRouter's Responses APIs are in beta. Anthropic, DeepSeek and the other chat completions providers do not serve the Responses API themselves, so Codex cannot reach them directly through OpenPike.
</Aside>

| | |
| --- | --- |
| OpenPike endpoint | `POST /v1/responses` |
| Base URL | `https://api.openpike.dev/v1` |
| Key | A virtual key, from the environment variable named in `env_key` |
| Models | `openai/<model>`, for example `openai/gpt-5.4`; also `xai/`, `groq/` and `openrouter/` models |
| Tags | `http_headers` in the provider config |

## 1. Add a provider key and create a key for Codex

Add your OpenAI API key (or an xAI, Groq or OpenRouter key) on the **Providers** page. Then, on the **Keys** page, create a virtual key for Codex and set it as an environment variable:

<Tabs syncKey="shell">
<TabItem label="bash">

```bash
export OPENPIKE_API_KEY="opk_live_..."
```

</TabItem>
<TabItem label="PowerShell">

```powershell
$env:OPENPIKE_API_KEY = "opk_live_..."
```

</TabItem>
</Tabs>

## 2. Configure Codex

Add a model provider to `~/.codex/config.toml` and make it the default:

```toml title="~/.codex/config.toml"
model = "openai/gpt-5.4"
model_provider = "openpike"

[model_providers.openpike]
name = "OpenPike"
base_url = "https://api.openpike.dev/v1"
env_key = "OPENPIKE_API_KEY"
wire_api = "responses"
http_headers = { "x-openpike-tags" = "agent=codex" }
```

- `model` is OpenPike's `provider/model` name. An [alias](/docs/features/aliases-and-fallbacks/) made for the Responses endpoint works too, for example `openpike/codex`.
- `env_key` names the variable Codex reads the virtual key from. Codex sends it as `Authorization: Bearer`.
- `wire_api = "responses"` is Codex's only supported value, and the format OpenPike serves at `/v1/responses`.
- `http_headers` adds `x-openpike-tags` to every request, so Codex's requests show as the agent `codex` in Logs, Activity and Agents.

### A run ID per task

A [run budget](/docs/features/run-budgets/) caps one task's spend, requests and time. `http_headers` values are fixed, but `env_http_headers` maps a header to an environment variable, so each task can carry its own run ID:

```toml title="~/.codex/config.toml"
[model_providers.openpike]
# ...as above, plus:
env_http_headers = { "x-openpike-run" = "OPENPIKE_RUN", "x-openpike-run-label" = "OPENPIKE_RUN_LABEL" }
```

<Tabs syncKey="shell">
<TabItem label="bash">

```bash
OPENPIKE_RUN="triage-$(date +%s)" OPENPIKE_RUN_LABEL="Nightly triage" codex exec "triage the open issues"
```

</TabItem>
<TabItem label="PowerShell">

```powershell
$env:OPENPIKE_RUN = "triage-$(Get-Date -UFormat %s)"
$env:OPENPIKE_RUN_LABEL = "Nightly triage"
codex exec "triage the open issues"
```

</TabItem>
</Tabs>

Once the run reaches a cap, Codex's requests get `429 run_limit_exceeded` and the task stops. Set a new `OPENPIKE_RUN` for each task.

To keep your normal Codex setup and use OpenPike only sometimes, leave out the first two lines and pick the provider per run: `codex -c model_provider=openpike -m openai/gpt-5.4`.

### Groq models

Codex also works with Groq models through OpenPike's Responses endpoint: add your Groq key on the **Providers** page and change the model line. The provider block stays the same.

```toml title="~/.codex/config.toml"
model = "groq/openai/gpt-oss-120b"
```

Everything after `groq/` is Groq's own model ID, here OpenAI's open-weight `gpt-oss-120b` as Groq serves it. Groq's Responses API is in beta, and its built-in tools (browser search, code execution) work only on `openai/gpt-oss-20b` and `openai/gpt-oss-120b`, according to Groq's docs. Groq's GPT OSS and Qwen models are priced from Groq's own models page, so their requests show a cost; Groq's Llama models are sold through its sales team, have no public price, and show tokens only.

## 3. Check it

Run a small task, then open **Logs**: each Codex turn is a request on the Responses endpoint, tagged `agent=codex`, with its tokens and cost.

```bash
codex exec "List the files in this directory and say which one is largest."
```

## What to know

- **Requests Codex makes:** only `POST /v1/responses`, streamed, with `store: false`, so each request carries the whole conversation and OpenAI keeps no state. When Codex compacts a long thread it sends that through `/v1/responses` as well. Every request counts toward your plan's monthly requests and your budgets.
- **Budgets and loop limits** apply as for any agent. A hard budget or a loop pause stops Codex with a `429`; see [Stop a runaway agent](/docs/recipes/stop-a-runaway-agent/).
- **Hosted tools** such as web search are billed by OpenAI on top of tokens, and are not in OpenPike's cost. See [Usage and cost](/docs/features/usage-and-cost/#hosted-tools-are-not-included).
- **Background responses** (`background: true`) are not supported by OpenPike. Codex does not use them.
